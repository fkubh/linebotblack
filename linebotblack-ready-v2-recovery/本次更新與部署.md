# 2026-10-16：啟動與 Google 429 修正版

版本：reliable-inbox-v1.1-startup。

你最後一張截圖顯示正確的 Gunicorn 啟動指令，以及 before-sheet-init 的程序峰值約 57MB。這行 WARNING 是診斷紀錄，本身不是 OOM 或啟動失敗；截圖沒有後續錯誤，也沒有 STORAGE READY，因此無法由它判定訂單功能是否已就緒。

本次針對先前的 Google 429 與啟動流程做修正：

1. 先載入網頁服務，再由單一背景執行緒初始化訂單與收件匣。資料初始化失敗不會直接讓 worker 結束，等待冷卻後重試。
2. 加入 `/ready`，資料尚未載入時回傳 503。真實訂單訊息也回傳失敗，不會被當成已保存。
3. 快取試算表結構資訊五分鐘；程式寫入成功或結果不明時會使快取失效，避免新增資料超出舊列數範圍後讀不到。
4. 收件匣僅含事件 ID／狀態的掃描，每次讀 5000 列；含訂單原文的歷史資料維持每次 500 列。仍掃描完整範圍，中間空白頁不會截斷。
5. 單一程序將讀、寫各限制在每分鐘最多 45 次呼叫。背景初始化達到限制時等待；即時訂單處理會延後並保留失敗／待處理狀態，不等待整分鐘占住請求。
6. 遇到 429 至少冷卻 60 秒；不再一秒後立即連續查詢。收到數字形式的 Retry-After 時，會採用較長的等待時間。
7. 原有收件保存、原子提交、去重、補處理、待人工確認、管理員指令及簡表警示保持不變。

45 次是此程序的保守上限，不是共享服務帳戶的全域配額鎖。若其他服務持續使用同一帳戶，仍可能收到 429。這版也不保證任何資料量都低於 512MB。

## 更新步驟

1. 暫停 Apps Script 的補處理觸發器，避免更新期間仍呼叫舊服務。保留原試算表及收件匣資料，不要刪除。
2. 使用本包整套檔案覆蓋 GitHub 應用根目錄。**除了 lineborblack_cloud.py、reliable_orders.py，這次還新增 sheets_runtime.py，務必一起上傳。**
3. 保留之前已設定的 REPLAY_SECRET、LINE Token、Google JSON、各試算表 ID、群組 ID、管理員 ID 與收件匣分頁名稱。
4. Build Command：`pip install --no-cache-dir -r requirements.txt`
5. Start Command：`gunicorn --config gunicorn.conf.py lineborblack_cloud:app`
6. **本次將 Render 的 Health Check Path 改成 `/ready`。**首頁 `/` 只表示網頁程序能回應，不能用它判斷訂單已就緒。現有服務需在 Dashboard 手動改；render.yaml 已同步更新。
7. 維持一個 worker、一個 thread。移除會覆蓋設定的舊 GUNICORN_CMD_ARGS；Python 版本延用 .python-version 的 3.11 系列。
8. 等待現有 API 壓力冷卻後，只部署一次，避免連續手動重啟。若有其他舊 Bot 同時使用同一服務帳戶，先停用重複服務。

## 怎樣算真正完成啟動

日誌會依序出現：

```text
[STORAGE INIT] loading order history
[STORAGE INIT] loading inbox index
[BOOT MEMORY] stage=after-sheet-init ...
[STORAGE READY] orders and inbox ready
```

遇到限流，可能先看到 `[SHEETS QUOTA]`，背景會等待，不必立刻重新部署。

- `https://你的服務.onrender.com/`：200 代表網頁程序可回應；若有 `storage=NOT_READY`，還不能處理訂單。
- `https://你的服務.onrender.com/ready`：**必須看到 `"ready": true` 且 HTTP 200，才算訂單資料已就緒。**初始化中會是 503。
- LINE「版本」：就緒後應顯示 reliable-inbox-v1.1-startup。

Render 使用 /ready 決定新版本是否可接收流量；官方目前給新部署最多十五分鐘通過健康檢查。若大量歷史資料或共享配額問題一直無法解決，部署仍可能失敗，但不能藉由把健康檢查改回 `/` 就宣稱訂單功能已修好。

完成就緒後，再恢復 Apps Script 排程；原本的自動補處理.gs、指令碼屬性與 REPLAY_SECRET 可繼續使用。保持 LINE 的 Use webhook 及 Webhook redelivery 開啟。LINE 的空事件 Verify 成功不代表資料已就緒，仍應確認 /ready。

用測試群驗證一筆完整訂單、取消／恢復、黑名單回覆和「漏單檢查」，並核對 Sheets。新版本不會自動恢復從未送達或舊版本未保存的訊息；已保存的待處理事件會沿用原收件匣繼續補處理。

## 驗證與限制

原本 26 項流程測試加上 8 項啟動／限流測試，共 **34 項本機模擬測試通過**。新增涵蓋：未就緒不確認訂單、背景初始化失敗可恢復、只啟動一個初始化執行緒、結構資訊快取與寫入失效、429 不立即重打、讀寫配額分離、5000 列索引掃描，以及初始化成功後可收單。

尚未連接你的 Render 與真實 Google Sheets，也未實測 Render Linux；本機測試不能當成正式環境已驗收。

本版在初始化期間有一條背景執行緒，負責 Google 資料讀取。訂單處理仍使用單一 sync worker，並在初始化完成前拒絕處理真實訂單事件，避免讀取半套資料。

參考：[Sheets 配額與退避](https://developers.google.com/workspace/sheets/api/limits)、[Render 健康檢查](https://render.com/docs/health-checks)。完整的收件匣、管理員及排程設定請見「部署指南.md」。
